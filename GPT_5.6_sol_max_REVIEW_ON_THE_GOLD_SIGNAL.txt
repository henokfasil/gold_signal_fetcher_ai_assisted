==================================================

Repository:
  /Users/henok/gold_signal_fetcher_ai_assisted

Review date:
  2026-07-23

Purpose:
  Assessment of whether this repository can become an AI-assisted XAUUSD
  signal-producing bot, including engineering, research-performance, AI,
  deployment, evidence-integrity, risk, and operational findings.


EXECUTIVE VERDICT
=================

This repository can become a solid AI-assisted XAUUSD signal bot.

The engineering and research foundation is valuable, but it is not currently
a validated signal producer. It is presently a paper-research candidate
collector with:

  - no validated ML artifact;
  - no demonstrated after-cost predictive edge;
  - zero approved VPS signals at the time of review;
  - a degraded prospective evidence-integrity status; and
  - an experimental Claude/sentiment layer that is not correctly wired or
    statistically validated.

The repository should not be abandoned. Much of the difficult plumbing already
exists: executable bid/ask data collection, causal candidate construction,
paper-only controls, append-only evidence, chronological evaluation, uncertainty
estimation, Telegram/dashboard infrastructure, and extensive tests.

The correct path is to preserve the reliable research baseline, repair release
and evidence integrity, rebuild the AI layer as an auditable observation layer,
and then test genuinely new information prospectively. Coding can improve the
engineering quickly; proving signal quality requires new information and future
evidence.

WHAT THE REPOSITORY DOES WELL
=============================

The strongest parts of the system are:

  - Paper-only enforcement: PAPER_TRADING must remain true.
  - No broker-order path in the reviewed runtime.
  - Independent Dukascopy bid and ask collection.
  - Executable-side targets: BUY enters at ask and exits/tests on bid; SELL
    enters at bid and exits/tests on ask.
  - Forming-bar exclusion and cadence/source/freshness validation.
  - Explicit handling of ambiguous same-bar TP and SL touches.
  - Chronological folds and actual-label-exit purging.
  - Dependence-aware weighting and calendar-week bootstrap intervals.
  - Separate BUY and SELL eligibility.
  - Hash-locked research contracts for several completed experiments.
  - Honest rejection of failed models instead of creating synthetic fallbacks.
  - Sixty existing unit tests passed during the local review.

These are meaningful assets and provide a substantially better base than
starting a new bot from scratch.


CRITICAL ENGINEERING AND OPERATIONAL FINDINGS
=============================================

1. GitHub, local, and VPS states are not reproducibly aligned
------------------------------------------------------------

At review time:

  - GitHub master revision was 5f0f82f.
  - Local HEAD was eb28273, one commit ahead of GitHub.
  - The local worktree contained many untracked files.
  - VPS Git HEAD was 5f0f82f, but the VPS was running manually modified and
    untracked files.

Several VPS runtime files had the same content hashes as the newer local
working files, but those changes were not represented by the VPS Git revision.

A clean archive of local HEAD could not import main_orchestrator.py because
agent/claude_decision_optimizer.py was referenced but was not tracked by Git.
Therefore the latest local commit was not a self-contained deployable release.

The VPS also contained an untracked .env.pre-919475c file. Its contents were
not inspected, but an environment backup inside a public-repository worktree is
an unnecessary accidental-secret-commit risk.

Required improvement:

  - Preserve ledgers before deployment work.
  - Create one clean, reviewed, self-contained commit.
  - Verify that a clean clone installs, imports, tests, and starts.
  - Deploy that exact SHA to VPS.
  - Display the runtime Git SHA and dirty/clean state on the operations
    dashboard.
  - Ignore .env* while explicitly allowing .env.example.
  - Ignore local/raw/licensed datasets, runtime ledgers, logs, locks, and local
    virtual environments.


2. The new Claude optimizer does not control the decision
---------------------------------------------------------

The runtime currently performs two separate Claude calls:

  1. ClaudeDecisionOptimizer.analyze_signal().
  2. AITradingDecider.decide(), which calls the older ClaudeAnalyst.

The actual should_trade result comes from the older decision path. The new
optimizer's TAKE/SKIP result is ignored. The code only overwrites selected
Claude availability/confidence fields afterward.

The optimizer's size_lots recommendation is:

  - not applied to position sizing;
  - not persisted in the canonical ledger;
  - not mapped to XAUUSD contract value;
  - not translated to stop-distance risk; and
  - not used by Telegram.

This produced five reviewed VPS rows where the ledger said Claude was available
while the stored rejection reason still said AI_REVIEW_UNAVAILABLE.

Required improvement:

  - Use one LLM observation call, not two conflicting decision calls.
  - Keep it isolated from approval until prospectively validated.
  - Store one internally consistent LLM record per candidate.
  - Never allow the LLM to control size, stop, or target without a separate
    frozen and validated policy.


3. The optimizer receives incorrect/missing fields
--------------------------------------------------

The optimizer asks for:

  - smc_score;
  - rsi_14;
  - adx_14;
  - macd;
  - macd_signal; and
  - bb_width.

The scanner supplies fields such as:

  - score;
  - rsi_1h;
  - macd_1h;
  - signal_1h; and
  - nested mtf.smc.adx_15m and mtf.smc.rsi_15m.

Most of the advertised Claude technical analysis is therefore supplied as zero
or N/A. The optimizer's model identifier is also hard-coded rather than using
the configured model environment variable.

Required improvement:

  - Introduce a typed canonical LLM input schema.
  - Build and test one adapter from scanner output to that schema.
  - Reject the LLM observation if required facts are missing.
  - Record model ID, prompt version/hash, supplied facts, raw response, parsed
    response, latency, timestamp, and error status.


4. The LLM design would contaminate a frozen experiment
-------------------------------------------------------

The optimizer supplies recent wins, losses, and average return to Claude.
If this output affected decisions, the policy would adapt to interim outcomes.
That conflicts with a frozen no-peek prospective evaluation unless the exact
online adaptation rule was registered before the experiment.

Required improvement:

  - Do not provide rolling outcomes during a frozen evaluation.
  - Freeze the prompt and input schema.
  - Treat a future adaptive policy as a separate registered experiment.


5. The dashboard overstates what is live
----------------------------------------

The dashboard advertises:

  - "Claude Decision Optimizer";
  - TAKE/SKIP decisions;
  - dynamic position sizing;
  - high-confidence win rate; and
  - "Live" status.

However:

  - TAKE/SKIP is derived from final APPROVE/REJECT, not the optimizer response.
  - Dynamic sizing is not applied.
  - No validated ML model exists.
  - All reviewed VPS candidates were rejected.
  - The new dashboard removed the integrity, context, pilot, and feed details
    that are more important at this research stage.

Required improvement:

  - Make operations and evidence integrity the primary dashboard.
  - Clearly separate:
      CANDIDATE,
      REJECTED,
      LLM OBSERVATION,
      VALIDATED PAPER SIGNAL.
  - Never label an unvalidated AI component as an optimizer.
  - Keep interim frozen-experiment performance blinded.


6. Evidence integrity is currently degraded
-------------------------------------------

The VPS evidence monitor reported:

  - technical feature schema drift;
  - two invalid context feature rows;
  - technical-feature reconciliation failure; and
  - context-observation reconciliation failure.

The technical problem has a concrete cause: rr_ratio is included in
ForwardFeatureJournal candidate metadata and also in
GoldFeatureEngineer.FEATURE_COLS. The generated CSV header therefore contains
rr_ratio twice, which pandas mangles and reorders during reading.

The two invalid context rows claimed complete captures while containing missing
24-hour realized-volatility values.

Required improvement:

  - Do not silently rewrite the frozen ledger.
  - Preserve hashes and original files.
  - Create a versioned repair/migration manifest or a new forward feature ledger.
  - Add an exact header test that reads the generated CSV through pandas.
  - Require the evidence monitor to be HEALTHY before considering the collection
    suitable for evaluation.


7. The sentiment experiment is not valid
----------------------------------------

The registered contract describes TradingView MCP/CryptoSieve-based Reddit,
news, macro-narrative, and sentiment inputs.

The deployed collector instead uses yfinance transformations of:

  - GC=F price momentum;
  - EURUSD momentum;
  - nominal 10-year Treasury yield momentum; and
  - VIX momentum.

These are price-based proxies. They are not:

  - gold news sentiment;
  - real rates;
  - geopolitical event risk; or
  - the provider and information source registered by the contract.

Additional problems:

  - the feature-schema hash remains "to_be_computed";
  - the contract is not runtime hash-locked;
  - the snapshot is overwritten every scan;
  - no append-only candidate sentiment ledger exists;
  - the orchestrator does not consume or journal the sentiment snapshot;
  - one benchmark uses random placeholder fold results and hard-coded metrics;
  - the "fast" benchmark manufactures sentiment from existing SMC indicators;
  - at least one fast benchmark gate is forced to pass.

Required improvement:

  - Declare the present sentiment experiment invalid/incomplete.
  - Prevent its reports from being interpreted as research evidence.
  - Remove placeholder benchmark paths from normal commands.
  - If sentiment is revisited, register the exact real provider and retain raw,
    timestamped, point-in-time text/source provenance.
  - Store one immutable sentiment observation per candidate.


8. Risk sizing is static and incomplete
---------------------------------------

RISK_PER_TRADE_PCT is configured but unused. The current ledger uses a static
$5,000 paper notional and can permit up to 15 open positions. This makes stop
risk vary with signal geometry and can create large aggregate exposure.

Daily and weekly loss caps use realized P&L but do not limit total planned stop
risk across open positions.

Required improvement:

  - Calculate paper notional deterministically from:
      account equity,
      configured risk budget,
      entry-to-stop distance,
      XAUUSD contract/multiplier semantics,
      spread/slippage assumptions.
  - Enforce maximum aggregate open stop risk.
  - Enforce gross-notional and correlated-direction exposure caps.
  - Keep all sizing deterministic; do not scale by uncalibrated LLM confidence.


9. Paper-trade exits are weaker than shadow outcomes
----------------------------------------------------

Approved paper positions are updated from the latest scan-time midpoint close.
This can miss an intraperiod TP or SL and does not use direction-correct
executable bid/ask highs and lows.

The shadow-outcome journal already has the stronger barrier engine.

Required improvement:

  - Reuse one execution-aware completed-bar lifecycle engine for paper positions
    and research outcomes.
  - Preserve the distinction between ambiguous same-bar touches and known exits.
  - Include spread and slippage consistently.


10. Cheap vetoes occur after expensive Claude calls
---------------------------------------------------

Recent VPS signals commonly had R:R values around 0.22 to 0.82, below the
minimum 2.0 requirement. Nevertheless, unique candidates could trigger two
Claude calls before the deterministic minimum-R:R risk veto was applied.

No validated ML artifact exists, which is already a mandatory veto, yet the LLM
is still called.

Required improvement:

  - Apply source, geometry, minimum-R:R, model-availability, exposure, and
    deterministic risk gates before any paid decision call.
  - If an isolated LLM research observation is still desired, make exactly one
    independently journalled call and never present it as an approval.


11. Public dashboard security is insufficient
---------------------------------------------

The dashboard was running with the Werkzeug development server on
0.0.0.0:8502, plain HTTP, without nginx, authentication, TLS, or an active UFW
firewall.

Required improvement:

  - Bind the application internally.
  - Place it behind a reverse proxy.
  - Add HTTPS and authentication.
  - Restrict administrative access by firewall/VPN where practical.
  - Do not expose detailed experimental or operational information publicly.

CORRECT ROLE FOR AI/CLAUDE
==========================

Claude should initially be an auditable observation and explanation component,
not the source of assumed alpha.

Good roles:

  - Transform timestamped news and macro releases into a fixed schema.
  - Detect stale, missing, contradictory, or malformed evidence.
  - Identify a pre-registered exceptional-event risk category.
  - Explain why deterministic and ML components accepted or rejected a
    candidate.
  - Produce an immutable research feature for later chronological comparison.

Poor roles:

  - Invent a confidence percentage from technical indicators.
  - Change TP or SL ad hoc.
  - Set arbitrary lots.
  - React to interim wins/losses during a frozen experiment.
  - Override a failed or unavailable ML model.
  - Turn generic market commentary into a claim of predictive edge.


HIGH-INFORMATION RESEARCH ROADMAP
=================================

Phase 0: Stabilize engineering
------------------------------

  1. Preserve and hash current VPS ledgers.
  2. Disable misleading optimizer/sentiment claims.
  3. Produce one clean, tested release commit.
  4. Align GitHub, local, and VPS on the same SHA.
  5. Repair/version evidence schemas.
  6. Restore the operational integrity dashboard.
  7. Add HTTPS, authentication, and network restrictions.

Phase 1: Implement the prospective event journal
------------------------------------------------

This is already identified by the repository's rigorous research protocol as
the next high-information task.

  - Use the same stable event IDs and 55-field causal schema.
  - Record only first-observable completed-bar events.
  - Keep the journal outcome-blind.
  - Validate event rate, duplicate rate, missingness, cadence, and feature drift.
  - Compare historical and runtime feature calculations for exact concordance.
  - Keep it isolated from approval, Telegram, and broker behavior.

Phase 2: Build a valid LLM observation ledger
---------------------------------------------

For every candidate/event, persist:

  - candidate/event ID;
  - exact source timestamps;
  - exact supplied facts;
  - prompt version and SHA-256;
  - model identifier;
  - raw response;
  - schema-validated response;
  - latency, token/cost metadata when available;
  - error status;
  - code and contract revision.

No decision effect should exist until a separately frozen comparison passes.

Phase 3: Add genuinely new causal information
---------------------------------------------

Do not add more transformations of the same XAUUSD OHLC history and expect a
new model class to create information.

Candidate information families:

  - Official CPI/NFP release clocks and published values.
  - FOMC statement and press-conference event windows.
  - BEA PCE release times and published values.
  - Properly archived actual-minus-consensus surprises, if a legally usable
    point-in-time source is available.
  - CFTC gold Commitments of Traders positioning and changes.
  - Genuine GC futures volume/open interest, curve, basis, roll, and options
    information where licensing permits.
  - Exact distance-to-event and post-release regimes.
  - Independently timestamped news text transformed by the frozen LLM schema.

All sources require:

  - exact identity;
  - availability timestamp;
  - publication lag;
  - revision policy;
  - missingness policy;
  - licensing/redistribution review; and
  - backward-only joins.

Phase 4: Use a simple model ladder
---------------------------------

Evaluate every new information set using the same folds, purge, costs, weights,
threshold and uncertainty method:

  1. Trade-all/constant/direction/event-type controls.
  2. Regularized linear expected-return or ranking model.
  3. Shallow XGBoost/CatBoost/LightGBM with fixed complexity.
  4. Calibrated abstaining ensemble only if components add fold-level value.
  5. Sequence/deep models only after the new information and effective sample
     size justify them.

Do not shop model classes on the already-inspected 2020-2026 outcomes.

Phase 5: Focus promotion research on BUY first
----------------------------------------------

BUY has the only historically interesting point estimates, although none is
validated. SELL is consistently weak.

Recommended policy:

  - Continue collecting both directions for honest comparison.
  - Keep SELL shadow-only.
  - Register a BUY-specific new-information hypothesis.
  - Require BUY to pass all gates independently.
  - Do not combine BUY and SELL to hide a weak side.

Phase 6: Frozen forward confirmation
------------------------------------

A component becomes eligible for paper-signal approval only after:

  - data integrity passes;
  - it beats a registered simple baseline;
  - selected after-cost expectancy is positive;
  - the dependence-aware lower confidence bound is above zero;
  - sufficient raw/effective observations and calendar blocks exist;
  - multiple folds and regimes are positive;
  - cost stress does not erase the result;
  - BUY/SELL eligibility is independent; and
  - dataset, code, schema, parameters, model, calibration, and prompt are
    hash-locked.

Passing historical development gates is not final proof. A frozen future paper
test is still required.


WHAT THIS BOT CAN REALISTICALLY BECOME
======================================

Near-term:

  An honest AI-assisted XAUUSD research candidate bot that:

  - collects validated data;
  - identifies structural BUY/SELL events;
  - produces auditable candidate geometry;
  - obtains one structured AI risk/news observation;
  - records every decision and failure;
  - sends clearly labelled research-candidate alerts; and
  - never implies that candidates are validated trade recommendations.

Longer-term:

  A validated paper signal bot, but only if a specific BUY or SELL component
  demonstrates positive after-cost expectancy with adequate uncertainty and
  frozen forward evidence.

Not currently justified:

  - live-capital execution;
  - commercial profitability claims;
  - Claude-controlled dynamic sizing;
  - "high-confidence" signal marketing;
  - claiming that four weeks or a 55% win rate alone proves an edge.


FINAL RECOMMENDATION
====================

Do not discard the repository.

Treat commit 5f0f82f as the last clearly reproducible rigorous research baseline
until the later prototype is cleaned, reviewed, and committed properly.
Preserve the later Claude/sentiment work as an unvalidated prototype rather
than production evidence.

The most effective next sequence is:

  1. Clean release and deployment integrity.
  2. Healthy evidence collection.
  3. Prospective stable event journal.
  4. One isolated and auditable Claude observation layer.
  5. Genuinely new macro/event/positioning information.
  6. BUY-first, leakage-safe model comparison.
  7. Frozen forward paper confirmation.
  8. Only then enable a "VALIDATED PAPER SIGNAL" output.

Overall assessment:

  - Engineering potential: strong.
  - Research discipline in the earlier baseline: strong.
  - Current predictive evidence: insufficient.
  - Current Claude optimizer: incorrectly integrated and unvalidated.
  - Current sentiment experiment: invalid/incomplete.
  - Suitability for paper candidate collection after immediate repairs: yes.
  - Suitability for dependable live-capital signals today: no.
  - Potential to become a serious AI-assisted gold signal system: yes, provided
    the repository follows the staged evidence-first roadmap above.
